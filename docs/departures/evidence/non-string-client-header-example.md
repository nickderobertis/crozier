# A boolean or integer client header is constructed from a string placeholder

**Kind:** `fern-defect`, the standing kind "a `YOUR_*` placeholder for a
non-string type". The independently authored
[Harbor Ledger document](../../fern-measurements/handed-off/snippet-rendering/snippet-rendering/openapi.yml)
declares three header parameters on every operation, which both generators
promote to required client constructor arguments: `X-Strict-Mode`
(`type: boolean`), `X-Tenant-Code` (`type: string`) and `X-Shift-Number`
(`type: integer`). Its unedited complete certified tree sits beside it as
`fern-expected/`, generated by Fern CLI 5.163.1 with
`fernapi/fern-python-sdk` 5.41.3 (packaged preview layout, organization/package
`fern`, project `default_package_name`, no audience filter,
`pydantic_config.enum_type: python_enums`).

The certified constructor annotates `strict_mode: bool` and `shift_number: int`
(`src/fern/client.py` lines 78 and 80), yet every docstring example constructs
the client with `strict_mode="YOUR_STRICT_MODE"` and
`shift_number="YOUR_SHIFT_NUMBER"`: the root clients' class docstrings
(`src/fern/client.py`, `strict_mode` on lines 67 197) and each method's
(`src/fern/berths/client.py`, on lines 53 88 144 187). The string header's
`tenant_code="YOUR_TENANT_CODE"` is the right type and stays. The same
placeholder reaches a real document: arawa/workspace's boolean `OCS-APIRequest`
header is `ocs_api_request="YOUR_OCS_API_REQUEST"` in its docstrings. The
README and `reference.md` constructions leave such headers out altogether
(measured beside this, and matched).

## Executed certified-output evidence

With the SDK's HTTPX and Pydantic dependencies installed, execute the committed
[proof script](non-string-client-header-example.py) against the certified tree:

```sh
python docs/departures/evidence/non-string-client-header-example.py \
  docs/fern-measurements/handed-off/snippet-rendering/snippet-rendering/fern-expected/src \
  --expected invalid
```

Run on 2026-11-03 (Python 3.14, HTTPX 0.28.1, Pydantic 2.14.0), it exited 0 and
printed:

```text
{"constructions": {"AsyncFernApi shift_number": "'YOUR_SHIFT_NUMBER' rejected by the int annotation", "AsyncFernApi strict_mode": "'YOUR_STRICT_MODE' rejected by the bool annotation", "BerthsClient.list_berths shift_number": "'YOUR_SHIFT_NUMBER' rejected by the int annotation", "BerthsClient.list_berths strict_mode": "'YOUR_STRICT_MODE' rejected by the bool annotation", "FernApi shift_number": "'YOUR_SHIFT_NUMBER' rejected by the int annotation", "FernApi strict_mode": "'YOUR_STRICT_MODE' rejected by the bool annotation"}, "sent_headers": [{"X-Shift-Number": "YOUR_SHIFT_NUMBER", "X-Strict-Mode": "YOUR_STRICT_MODE", "X-Tenant-Code": "YOUR_TENANT_CODE"}]}
```

The script imports the actual certified package, parses the client construction
out of the sync and async root client docstrings and a method docstring with
Python's AST, reads the actual constructor's annotations with
`typing.get_type_hints`, and validates each value with Pydantic's strict type
validator: both non-string placeholders are rejected. It then constructs the
client exactly as documented and sends a request through a local HTTPX
transport: the placeholders go on the wire as the headers' values. Run the same
way over crozier's generated tree with `--expected valid`, `strict_mode=True`
and `shift_number=1` validate and are sent as `True` and `1`.

## The rule

`non_string_client_header_example` admits only a `client.py` docstring line
(never a raw client or the Markdown files) whose sole change replaces
`<name>="YOUR_<NAME>"` with the generator's own placeholder for the declared
type, `True`, `1` or `1.1`, for a header the source document declares
`boolean`, `integer` or `number` and whose promoted argument is `<name>`.
A string header, a query parameter of the same name, any other value or
indentation, and a missing source document still fail. The unit test
`non_string_client_header_examples_admit_only_the_declared_type` holds those
cases; the measurement's crozier-e2e journey compares the whole tree with this
departure applied and fails an unexplained byte beside it.
