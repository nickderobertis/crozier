# An int64 example rounded past the format's bounds

The independently authored
[`odometer-reading`](../../openapi-surface/handwritten/odometer-reading/openapi.yml)
source posts a body whose `metres` property is `type: integer`, `format: int64`
with the example `9223372036854775807`, the int64 maximum, beside a
`trip_count` of the same format exampled `9007199254740993`. Its complete
unedited certified tree was generated by Fern CLI 5.67.1 and
`fernapi/fern-python-sdk` 5.20.0 (packaged preview layout, organization and
package `fern`, project `default_package_name`, no audience filter,
`pydantic_config.enum_type: python_enums`); the companion overlay under
[`docs/fern-measurements/literals-mode/odometer-reading`](../../fern-measurements/literals-mode/odometer-reading/)
records the same source with `enum_type` unset.

Fern reads the document's numbers as JavaScript doubles, so every integer
example above 2^53 is written as the double nearest it. For `trip_count` that
is `9007199254740992`: a different integer than declared, but a valid int64,
and crozier writes it exactly as Fern does. For `metres` the nearest double is
2^63, which Fern spells `9223372036854776000` in the README, `reference.md` and
both client docstrings. That value exceeds the int64 maximum the property
declares, so the documented example is invalid for its own schema. crozier
writes the declared `9223372036854775807` there instead and nowhere else.

## Executed certified-output evidence

The committed [validator](int64-example-rounded-out-of-range.py) imports the
generated package, evaluates every worked call of the operation — the sync and
async client docstrings, both README usage blocks and the `reference.md`
example — binds each docstring call to the actual generated method with
`inspect.signature`, and checks each argument the source declares
`format: int64` against the signed 64-bit bounds and the declared example.
Executed on 2026-10-10 with Python 3.14 and PyYAML 6.0.3 from the repository
environment:

```sh
PYTHONDONTWRITEBYTECODE=1 python docs/departures/evidence/int64-example-rounded-out-of-range.py \
  docs/openapi-surface/handwritten/odometer-reading/fern-expected \
  docs/openapi-surface/handwritten/odometer-reading/openapi.yml \
  --operation-id recordReading --method record_reading --examples invalid
```

It exited 0, reporting for each of the five calls:

```text
"metres": "9223372036854776000 exceeds the int64 bounds (-9223372036854775808, 9223372036854775807)", "trip_count": "in range"
```

The same command with `--examples valid` exits 1 on the certified tree. Over a
tree the compiled crozier binary generated from the same source
(`crozier --no-config generate python --spec … --package-name fern
--project-name default_package_name`) it exits 0 with `--examples valid`,
reporting `"metres": "the declared example, in range"` for every call; the
literals tree reads the same.

## The parity rule

The rule accepts one aligned line pair of `README.md`, `reference.md` or a
client docstring's `Examples`, equal but for one integer keyword value, when
crozier's value is an int64 example the parsed source document declares, Fern's
is the JavaScript spelling of that value's nearest double, and Fern's lies
outside the signed 64-bit range. Without the source document, for a value the
document does not declare, for an in-range rounding, or outside an example, it
does not apply. The line ledger is recorded from `src/parity.rs`, never
hand-edited.
