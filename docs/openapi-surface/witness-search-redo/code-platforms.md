# Code and platform source report

shard: `code-platforms`

This report owns Sourcegraph, GitHub code search, SwaggerHub, and Postman. The
queries below were run on 2026-09-09. A numeric result is a declaration count
from the existing selector evaluator over fetched blobs, not an index-match count.
An `unanswered` result records a limiter or a body-inaccessible family; partial
body hits were still fetched and evaluated before that classification.

## Controls, returned bodies, and failures

- **Sourcegraph:** the control `curl -sS -G https://sourcegraph.com/.api/search/stream --data-urlencode v=V3 --data-urlencode 'q=repo:Kitware/VolView file:openapi.json content:"propertyNames" count:20 type:file'` returned HTTP 200, `matchCount: 7`, no skipped reason, and the known declarer. Archived and fork exclusions are not treated as refusals. Every general funnel uses separate `content:` clauses for nonadjacent structure and runs YAML, YML, and JSON spellings. The returned pages yielded **23 distinct plausible OpenAPI blobs**: all 9 YAML blobs fetched and parsed; 12 YML blobs fetched, 11 parsed and Authelia failed the evaluator's strict YAML reader at line 38; and the JSON pages' two plausible OpenAPI documents fetched, Kubernetes parsed with zero owned selectors while EmbedPDF exceeded a 120-second evaluator bound. Generated files, test fixtures, source-code files, and standalone JSON Schemas were identified by repository/path and excluded before fetch. The parsed bodies produced four positive key/document pairs, recorded below. Every other general funnel hit `shard-match-limit` in at least one spelling (the YAML `/anyOf/` stream ended without a terminal event), so its partial parse cannot establish absence and remains `unanswered`; the returned hits are not discarded or called inaccessible.
- **GitHub code search:** the original preflight `gh api rate_limit --jq '.resources.search'` returned limit 30, remaining 30. The control `gh api -X GET search/code -f q='"scheme" "bearer" filename:openapi.yaml' -f per_page=1` returned `total_count: 28928` and a real blob. That sweep then hit the secondary limiter while the primary endpoint still reported 30 of 30 remaining: the first refusal was HTTP 403, request `9D4A:ED00:24CD72:78CED4:6AA180BE`, at 2026-09-09 15:52:30 UTC; six already-issued loop iterations returned the same refusal family before the sweep stopped, and none was retried after inspection. On the later 2026-09-09 review, a fresh preflight reported `search 30/30`, `code_search 10/10`, `core 5000/5000`, and `graphql 5000/5000`, establishing that the burst limiter had cleared. The records nevertheless remain `unanswered` for an independent reason: GitHub code search can require literal terms in one blob, but cannot express schema position, array cardinality, sibling relation, or reference-target resolution for any of these 30 selectors. The two earlier answered calls returned zero literal-phrase matches, which are not declaration zeros; resuming those same literal calls would return index matches rather than answer the owned structural question, so no further code-search request was made. The historical 403 is preserved as sweep evidence and is not the basis for the current classification.
- **SwaggerHub:** the control `curl -sS -G https://api.swaggerhub.com/specs --data-urlencode query=petstore --data-urlencode limit=1` returned HTTP 200 and `totalCount: 129609`. Owned queries returned metadata counts from 0 through 803,130, but this endpoint searches names and descriptions and exposes mutable `owner/api/version` links rather than body matches or immutable references. These are metadata-only responses, never declaration zeros.
- **Postman:** the control `curl -sS https://www.postman.com/_api/ws/proxy -H 'content-type: application/json' --data '{"service":"search","method":"POST","path":"/search-all","body":{"queryIndices":["adp.api"],"queryText":"petstore","size":1,"from":0}}'` returned HTTP 200 and an API metadata hit. Every owned term was rerun at the reported valid maximum, `size: 25`, separately against all four families. `adp.apiDefinition` refused every request as an unallowed index; the other families returned API, specification-file, collection, or request metadata, not public definition bodies. The selector evaluator therefore had no Postman body to qualify.

The authoritative rows in `../schemas.md` remain unchanged.
