Every general funnel below returned `shard-match-limit` at 100 matches (the `/anyOf/` request ended without a terminal event), so those records remain `unanswered`, not zero. Its positive record carries the complete qualification and Fern refusal.
- **GitHub code search:** the required preflight `gh api rate_limit --jq '.resources.search'` returned limit 30, remaining 30. The control `gh api -X GET search/code -f q='"scheme" "bearer" filename:openapi.yaml' -f per_page=1` returned `total_count: 28928` and a real blob. The owned sweep then hit the secondary limiter while the primary endpoint still reported 30 of 30 remaining: the first refusal was HTTP 403, request `9D4A:ED00:24CD72:78CED4:6AA180BE`, at 2026-09-09 15:52:30 UTC. Six already-issued loop iterations returned the same refusal family before the sweep stopped; no call was retried after inspection and no further GitHub code-search call was made during this redo. The two calls answered before refusal returned zero literal matches, but literal search cannot express their structural selectors, so all GitHub records remain `unanswered`.
- **SwaggerHub:** the control `curl -sS -G https://api.swaggerhub.com/specs --data-urlencode query=petstore --data-urlencode limit=1` returned HTTP 200 and `totalCount: 129609`. Owned queries returned metadata counts from 0 through 803,130, but this endpoint searches names and descriptions and exposes mutable `owner/api/version` links rather than body matches or immutable references. These are metadata-only responses, never declaration zeros.
- **Postman:** the control `curl -sS https://www.postman.com/_api/ws/proxy -H 'content-type: application/json' --data '{"service":"search","method":"POST","path":"/search-all","body":{"queryIndices":["adp.api"],"queryText":"petstore","size":1,"from":0}}'` returned HTTP 200 and an API metadata hit. The selector evaluator therefore had no Postman body to qualify.
